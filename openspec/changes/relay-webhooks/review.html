Why

Relay keeps your notes, but you may want them in your own database too, next to your other data, in a shape you can rely on. A webhook sends each new note to an address you own, a few seconds after Relay gets it, in one documented format. You can build your own tools on your notes without asking Relay for them.

What Changes

  1. 1
    Relay sends your data on, in order, with nothing skipped. Your phone syncs to Relay's server. Then the server sends each new note to every webhook you added, a few seconds later. Each webhook keeps its place in a list of everything Relay stored. If your database is down, Relay keeps that place and tries again for a day. After that it waits for Try again now, then sends everything from where it stopped. A note that arrives twice has the same id, so your database keeps one copy.

  2. 2
    You choose what goes. Each webhook sends notes, with their words, recording and place. Health and location are sensitive, so they go only if you tick them for that webhook.

  3. 3
    A webhooks section on the Relay page. It lists each webhook with its last result. You can send a test, send past data from a date, make a new secret, pause it, or remove it. When you add a webhook, its secret shows once, so your database can check that each message came from Relay.

  4. 4
    Past data on request. A new webhook gets only new data. Send past data sends everything from a date you pick, in the same format, so your database can catch up.
  5. 5
    One set format, written down in public. Every message has the same envelope and a version number, and is signed by the open Standard Webhooks method, which has libraries for most languages. The Relay website gets a Your own database page with the format, an example receiver to copy and the tables to make in Postgres. It replaces the Coming note there.

Removing a webhook deletes its secret and its send history; this can't be undone. Your notes stay in Relay.

Non-goals: sending from the phone directly, writing into a database without a webhook, choosing your own format, sending to a person's AI (the MCP server plan), and end-to-end encryption.

It builds on the Relay app first version, which is now published.

What the build needs

  1. Ready Cloudflare token for the queues: CLOUDFLARE_API_TOKEN is in .env, and the account already runs queues.

  2. Ready A test address for your database: the build makes a throwaway receiver to test against. Your real database can come later.

Decisions

  1. asked2026-11-05

    Asked which data a webhook sends → chose notes always, with health and location ticked for each webhook.

  2. asked2026-11-05

    Asked what happens to earlier data when a webhook is added → chose new data only, plus a Send past data from a date button.

  3. asked2026-11-05

    Asked how a ring note's recording reaches the database → chose inside the message, as base64.

  4. asked2026-11-05

    Asked where the webhook sends from, given that Relay is offline by default → chose phone → Relay server → your database; only the server sends, and only data the server holds.

  5. asked2026-11-05

    Asked whether end-to-end encryption changes how webhooks send → chose no encryption: Relay goes fully open source, people who want protection host it themselves, and the server keeps building and sending each message.

  6. assumed2026-11-05

    Assumed: the format follows Standard Webhooks (webhook-id, webhook-timestamp, webhook-signature), because receivers in most languages can check it with a ready library.

  7. assumed2026-11-05

    Assumed: delivery runs on a Cloudflare Queue with backoff for about 24 hours, then the webhook shows as failing with a Try again now button, because a queue survives Worker restarts and the account already uses queues.

  8. assumed2026-11-05

    Assumed: every stored row also goes into a send list in the same database write, and each webhook keeps its place in that list, because the first version's saved code stores each item in one write, and a separate send record could be lost between two writes.

  9. assumed2026-11-05

    Assumed: health and location go as batches of up to 500 rows per message, not one message per row, because a sync sends hundreds of rows at once.

  10. assumed2026-11-05

    Assumed: each webhook gets messages in order, but a retry after a lost answer can repeat one, so every item has a stable id and a receiver upserts.

  11. assumed2026-11-05

    Assumed: only the owner, signed in as a person, manages webhooks; device keys can't, because a device key only sends data.

  12. assumed2026-11-05

    Assumed: a webhook address must be https and can't point at a private network, localhost or Relay's own site, because the server would otherwise call addresses for an attacker.

  13. assumed2026-11-05

    Assumed: the format page lives on the Relay website (site/), with its schema and example receiver as files there, because the website is public and relay-app is archived now that the whole project is one public repository.

  14. assumed2026-11-05

    Assumed: the webhooks section sits at the bottom of the Relay page, below the notes, because the page's main job is the timeline and you set up a webhook once.

  15. assumed2026-11-05

    Assumed: a note sent to the server later, when sending is turned on with earlier notes, goes out as note.created at that time, because the server sees it as new then.

  16. assumed2026-11-05

    Assumed: the seed webhook is paused and points at example.com, because a preview must never send made-up data to an outside address.

  17. assumed2026-11-05

    Assumed: the tables have a few columns the design did not name: tries, next_try_at, backfill_seq and last_sent_at on relay_webhooks, and logged_at on relay_outbox. They count the retries, stop a second retry chain, show Sending past data, and keep a message's timestamp the same on each retry.

  18. assumed2026-11-05

    Assumed: New secret asks for a confirmation first, because the old secret stops working at once.

  19. assumed2026-11-05

    Assumed: the sweep's manual trigger is POST webhooks/sweep, owner-only and refused on production, because the rule for timed jobs asks for a trigger that only staging answers.

  20. assumed2026-11-05

    Assumed: the local environment binds its own queue, relay-webhooks-local, and the queue router drops a -local end as it drops -staging, so wrangler dev runs the same code.

  21. assumed2026-11-05

    Assumed: the sender checks the address again before each send, but without the site's own host, because the queue has no request to read it from and the private address can't be written into the code.

  22. assumed2026-11-05

    Assumed: a run stops after 20 messages and queues itself again, and a ring note waits up to 2 minutes for its recording, so one run stays short and a note never goes out before its sound.

  23. assumed2026-11-05

    Assumed: the secret in the Secret, shown once picture is covered with dots, because the repository is public and its check does not read text in pictures. The prototype made that secret in the browser, so no server holds it.

  24. assumed2026-11-05

    Assumed: the Try it lines keep the preview's address, because the review page needs one link, the preview is behind a login, and the repository already names the site's address.

  25. log2026-11-05

    Built tasks 1.1 to 7.1. A second look found the sender kept an old lease time, so the send position never moved outside the tests; fixed, with a test whose clock moves. Saved for the preview check (7.2), merged with the AI connector change.

  26. log2026-11-05

    The preview check found a second lease slip: a run that stopped early, because a retry was already planned, gave its lease back with the old time, so the planned retry found the lease taken and was dropped. Fixed, with a test.

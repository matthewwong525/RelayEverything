# Relay Everything's space migrations

Each person's space runs the numbered SQL steps in `schema/space-migrations/` to build and change its tables. This page tells what each step does and the rules for a new one. It is part of [person spaces](relay-spaces.md).

A space runs [`schema/space-migrations/`](../schema/space-migrations/) in order, in its constructor under `blockConcurrencyWhile`, and records each in its `space_migrations` table. `0001_relay.sql` is the D1 `relay_*` schema as it was before spaces; [`space-schema.test.ts`](../app/worker/apps/relay/space-schema.test.ts) checks that a space holds each person's tables and D1 only the directory. `0002_space.sql` adds what only a space has: its file key, each Pebble device's signing secret (until `0005`), and the person the alarm sends for. `0003_api_devices.sql` widens `relay_devices.reaches` to `phone`, `chats`, `api` and `app`: an `app` row is a connected AI app's device, made on its first note, hidden from the page's device list, and turned off when the app is disconnected. `0004_attachments.sql` adds `relay_attachments`, the files listed on each note. `0005_no_pebble.sql` drops the Pebble signing secrets and the `relay_outbox_note_updated` trigger, because the Pebble route and late ring-note places are gone; a `note.updated` row already in an outbox still sends. `0006_phone_data.sql` rebuilds `relay_health` with no CHECK on `type`, so a new health type is one edit to `HEALTH_TYPES` in [`queries.ts`](../app/worker/apps/relay/queries.ts), not a table rebuild; rebuilds `relay_outbox` with the `calendar` kind; and adds `relay_calendar_events`. `0007_note_files.sql` rebuilds `relay_outbox` with the `note.file` kind, adds a trigger that logs a file when `POST attachments` seals its bytes, at its note's `recorded_at`, and logs each file already stored once. A calendar row is one occurrence of an event, unique by `(device_id, event_key)`; `POST calendar` ([`calendar.ts`](../app/worker/apps/relay/calendar.ts)) upserts only when a field differs, so a resend wakes no webhook, and a removed event keeps its row with `removed_at` set, which every read skips. `0008_photos.sql` adds `relay_photos`, one row per photo with its time, place and size, and rebuilds `relay_outbox` with the `photo` kind, so each new photo is logged for the webhooks. A staging space ran it first as `0007_photos`, before `0007_note_files`, so each of its steps is safe to run again, and `0007_note_files` takes `photo` rows too. `0009_inbox.sql` widens `reaches` again, with `inbox`: a way in's own device, such as *Email*, hidden from the page's device list. A staging space ran it first as `0007_inbox`, and it is safe to run again. `0010_note_edits.sql` adds `relay_notes.edited_at`, the Unix ms time the phone that sent a note last changed it, NULL for a note never changed. A staging space ran it first as `0008_note_edits`, so `migrate` skips it there by that name (`RAN_AS` in [`spaces-worker.ts`](../app/worker/spaces-worker.ts)): `ALTER TABLE … ADD COLUMN` can't run twice. `PATCH notes` ([`edit-note.ts`](../app/worker/apps/relay/edit-note.ts)) finds the note by its server `id`, any note in the space, or by `(device_id, client_id)` for the calling phone's own. It takes the phone's `editedAt`, clamped to the server's now so a clock set ahead can't lock a note, and answers `409` with no change when the stored `edited_at` is later: the newer change wins, whatever order the changes arrive in. Otherwise it changes the text, adds the files the server lacks (only to the phone's own note), and logs one `note.updated` at the note's `recorded_at`, after its `note.created`; the same words with no new file change nothing and log nothing. `0011_note_sync.sql` adds `relay_note_changes`, one row per note at its newest change: triggers delete the note's row and add it again after a note is added, after a change of its text, place, `edited_at` or recording, and after a file is listed or made ready, so `AUTOINCREMENT` gives it a higher `seq`. The triggers delete and add, not `INSERT OR REPLACE`, because an outer statement's conflict clause replaces a trigger's. It fills one row per note already there, oldest first. `GET notes?since=` reads the rows past a phone's last `seq`, in order, so a phone never misses or repeats a change across a page edge, as a time cursor would when two writes share a millisecond. `0012_note_deletes.sql` rebuilds `relay_note_changes` with no foreign key, plus `deleted` and `client_id`: a trigger moves a deleted note's row to a new `seq` with `deleted = 1` and the note's `client_id`, so each phone's next pull drops the note, also a phone that never got its server `id`. `GET notes?deleted=1` gives such a row as `{ id, clientId, deleted: true }`; without `deleted=1` it skips them, so an older phone sees no new shape. The rebuild copies each `seq` and the triggers again, as `0008_photos` does for `relay_outbox`, which it also rebuilds with the `note.deleted` kind. `0013_stays.sql` adds `relay_stays`, the stays and trips each phone works out from its points, unique by `(device_id, kind, start_at)`: a stay has `lat`, `lon`, `name`, `address`, `event` and `source`, a trip `mode` and `km`, and `ongoing` is 1 while the person is still there. `POST stays` ([`stays.ts`](../app/worker/apps/relay/stays.ts)) upserts only when a field differs, as `POST calendar` does, so a resend logs nothing; triggers log each new and changed row as a `stay`, at its `start_at`, and the step rebuilds `relay_outbox` with that kind, as `0012` does. The reads use the stays and trips, and the old street runs for points that no stay or trip covers, such as old days or a phone on *Only points*. A stay reads as `ongoing` only while its `end_at` or `updated_at` is within 6 hours. `0014_nights.sql` adds `relay_nights`, the nights each phone groups from its sleep readings, one per source, unique by `(device_id, source, start_at)`, with the minutes in each stage and the stage timeline as JSON in `stages`. `POST nights` ([`nights.ts`](../app/worker/apps/relay/nights.ts)) upserts only when a field differs, as `POST stays` does; triggers log each new and changed night as a `night`, and the step rebuilds `relay_outbox` with that kind. It also adds `kind`, `distance` and `calories` to `relay_health`, set only on a `workout`: a resend fills them on a row that has none, once, and a trigger logs that row as `health` again, so the webhooks get the workout with its details.

A new space table goes in a new numbered file: never edit one a space already ran. A step that rebuilds a table other tables point at sets `PRAGMA defer_foreign_keys = ON` first and `OFF` at its end: inside a Durable Object the setting otherwise lasts to the end of its transaction, and a later bad row resets the space. Try such a step on the local runtime with `wrangler dev`, because the tests' `node:sqlite` does not show it. SQLite can't change a CHECK in place, and `relay_devices` is a parent of foreign keys, so `0003` copies the rows out, drops the table, makes it again under its own name and copies them back, with `PRAGMA defer_foreign_keys = ON`, inside the one migration transaction. A rename of a new table fails the foreign keys.

`0017_note_places.sql` moves each note's place into `relay_locations` as one point at the note's `recorded_at`, then empties the note's place columns. They stay, never read: `DROP COLUMN` refuses a column the table's CHECK names, and dropping `relay_notes` to make it again deletes every note's files through `ON DELETE CASCADE`, even with the foreign-key check deferred. It drops `relay_outbox_location` around the copy and makes it again, so the moved points send no webhook message.

`0018_note_pins.sql` adds `relay_notes.pinned_at`, when the note was pinned, NULL when it is not, and `pin_changed_at`, when its pin last changed. `PUT notes/pin` ([`pin-note.ts`](../app/worker/apps/relay/pin-note.ts)) clamps the phone's `at` to the server's now and answers `409` when the stored `pin_changed_at` is later, as `PATCH notes` does for `edited_at`. A pin that already matches still saves its newer `at`, so an older change made elsewhere still loses. The answer gives `pinChangedAt` by the server's clock, and the phone keeps it, so a phone clock set ahead never beats a later pin. A trigger moves the note's `relay_note_changes` row when either column changes, so each phone's next pull gets the pin. It logs no `relay_outbox` row: a pin does not change the note, so no webhook gets a message.

To try a step on old rows, run the stack [on this computer](stack/relay-ai-connector.md#on-this-computer) and make a space with one request. Then stop the spaces Worker, write the old rows into the space's SQLite file in `app/.wrangler/state/v3/do/relay-everything-spaces-local-Space/`, and delete the step's row from `space_migrations`. Start the Worker again: the next request runs the step, and you read the rows from the same file.

# Design

## Context

The Relay Everything server (`app/wrangler.relay.jsonc`, worker `relay-everything-server`) checks each caller and opens only that person's space (`space.ts`). A computer key is a device key of kind computer (`sign-in/computer.ts`). The account already has Cloudflare Artifacts on Workers Paid; the admin app binds namespace `wongstack`. Artifacts gives a Workers binding: `create`, `get`, `delete`, `fork` on a namespace, and `createToken(scope, ttl)` on a repo handle. Git reaches `https://<account>.artifacts.cloudflare.net/git/<namespace>/<repo>.git` with `Authorization: Bearer <token>`. A repo can't be made with files, but can be forked.

## Goals / Non-Goals

**Goals:** one memory table, its columns and its routes; one repo per person; a pass route for computer keys; a start repo with the default rules; the plugin's copy and send; delete with the account.

**Non-Goals:** writing facts and pages from chats (part 2); the plugin's local copy of facts; reading pages first, search, the auto-look hook (part 3); a page in the phone or web app; webhooks for page changes; the connector reading pages.

## Decisions

- **Binding, not REST.** Add `"artifacts": [{ "binding": "KNOWLEDGE", "namespace": "relay-everything-knowledge" }]` to the server, `-staging` in its env. No Cloudflare token lives in the Worker. Wrangler goes to 4.145.0 or later, as the binding needs.
- **Repo name `p-<personId>`.** Person ids are already safe for names; a prefix keeps the first character a letter. The `.git` remote never holds the account id in a public file: the route answers it.
- **Make on first ask, by fork.** `POST /v1/knowledge/access`: `get(name)`; on missing, `fork` the namespace's `start` repo into it (`defaultBranchOnly`); a `forking` status waits briefly, else answers 503 with *try again in a minute*. Fork over `create`+push because the Worker can't push git objects.
- **Pass:** `repo.createToken("write", 3600)`. The answer: `{ remote, token, expiresAt }`. Only `asDevice` callers of kind computer; a phone key, an old chat-only key, a session or an API key get 403. Rate-limit by the existing per-key limits.
- **No binding → 501** `{ error: "not_set_up", error_description: "The knowledge web is not set up on this server." }`. Self-host docs say it needs Workers Paid.
- **Start repo.** `scripts/relay-knowledge-setup.mjs [--staging]` makes the namespace and the `start` repo, and pushes `schema/knowledge/README.md` and `FORMAT.md` to it with a short write token from `CLOUDFLARE_API_TOKEN`. Running it again updates the start pages; existing webs keep theirs (the plugin's part 2 can update an old web's `FORMAT.md`). `publish-relay-server.mjs` runs it before the server publish, so it is never missed.
- **One memory table, fixed in SQL; the person's columns are checked values.** `schema/space-migrations/0016_memory.sql` makes three tables the server alone writes:
  - `relay_memory`: the columns Relay Everything keeps, `id` (`f` + 4 to 6 base32 characters, made by the server, unique in the space), `sources` (a JSON array of `relay:` links; each tag, in `relay_memory_tags`, is `[a-z0-9-/]`), `replaces` (JSON array of ids), `replaced_by` (id or null), `device`, `client_id` (unique for each device, as for notes, so a resent batch is stored once and two computers never drop each other's fact), `created_at`; and `fields`, a JSON object with the person's columns. Index on `created_at`, and `relay_memory_tags (fact_id, tag)` for tag reads.
  - `relay_memory_columns`: `name` (1 to 30 of `[a-z0-9_]`, starting with a letter, not a kept name), `type` (`text` up to 400 characters, `number`, `date`, `yes_no`, `words`: a list of up to 20 short words), `required`, `note` (up to 200 characters, read by the AI), `removed_at`. At most 20 live columns. The migration seeds `kind` (text, required) and `text` (text, required).
  - `relay_memory_column_changes`: each change, with its device and time, read by `GET /v1/memory/columns?changes=1`.
  No caller's text ever becomes SQL: names are checked by pattern, filters bind values, and a JSON path is built only from a live column's checked name. So a caller reaches only these rows, and a column change needs no migration. Adding a fact checks each value against the live columns, and a required column on new facts only; an unknown column is refused. Adding a fact that replaces others sets their `replaced_by` in the same transaction; that is the only update, and no route deletes a fact.
- **Column changes:** `POST /v1/memory/columns` with `{ add: [{name,type,required,note}], change: [{name,required?,note?}], remove: [name] }`, all or nothing. A type change, a kept name, a 21st column, or adding back a removed name with a new type is refused. A removed column leaves its values in old facts, returned under `fields` as before; it is no longer checked or filtered. Computer keys only.
- **Routes**, in the web API beside the others and generated into the API doc: `POST /v1/memory` (computer keys; up to 50 facts a call, each with `clientId`); `GET /v1/memory?q=&tag=&source=&from=&to=&all=&limit=&cursor=` and `<column>=<value>` for any live column (word search over text and words columns, like notes: every word, any case); `GET /v1/memory/{id}` (the fact, what it replaced, what replaced it); `GET /v1/memory/columns`. Phone keys refused, as for chats. The connector gets `memory` (search, with the columns in its answer) and `read_fact` tools from the same answers (`inputs.ts`, `answers.ts`, `api.ts`), the tool count goes to 16, and the connector's instructions name the memory first for *what did I decide*.
- **Tags change; words don't.** `relay_note_tags (note_id, tag)` joins the memory's `relay_memory_tags`, and `relay_tag_changes (link, tag, change, device, created_at)` keeps each add and remove for both, in the same migration. `POST /v1/memory/{id}/tags` and `POST /v1/notes/{id}/tags` take `{ add: [tag], remove: [tag] }`, computer keys only; a fact's last tag can't go. `GET /v1/notes` and the connector's `search` take `tag=` (a tag matches itself and its children: `ring` finds `ring/charging`). A deleted note drops its tags. The JSON `tags` column on `relay_memory` goes away; the tag table is the one copy.
- **No AI on the server.** The server stores tags and answers lookups; part 2's helpers on the computer choose them, and part 3's `topic <name>` pull reads the local copy plus `facts --tag` and `notes --tag`, so this plan adds no topic route.
- **Plugins.** The same sign-in link that connects this plugin gives any plugin a computer key. A plugin builder gets the routes above and the web pass, and nothing more. The website page has a short part for them: connect, read `FORMAT.md` and the columns, add facts, open the web.
- **Plugin reads and adds**: `relay.mjs facts`, `fact <id>`, `add-facts` (JSON on stdin), `columns`, `change-columns` (JSON on stdin). Part 2's helpers use `add-facts`.
- **The default rules** (`FORMAT.md`), one screen, in three parts. *Facts:* kinds `fact`, `decision`, `preference`, `plan`, `open`, `reference` in `kind`; one short sentence in `text`; read the memory's columns and fill each one that fits; tags name topics; at least one source; replace, never repeat; added with `relay.mjs add-facts`. *Pages:* only `topics/`; a topic is made by its first fact, never seeded; one subject, one page; a big topic becomes a folder with `README.md` linking its sub-pages; kebab-case names; frontmatter `title`, `summary` (one line), `updated`; `README.md` lists the top-level topics with their summaries; a page sums up the live facts with its tag in plain sentences and lists no fact ids; a page links other pages by path; no page per chat. *Look:* read `README.md`, read the page, `relay.mjs facts --tag <topic>` and `notes --tag <topic>`, then open a source. *Links:* `relay:<kind>/<id>[#<message>]`; no health values or coordinates. `README.md` links the topics. The website page shows the default, with a check that it matches `schema/knowledge/FORMAT.md`; a person's own copy may differ, and nothing checks it against the default.
- **Rules are read, not enforced, except the columns.** The server takes any text in `kind`, checks each column's type and the required ones, and needs a tag and a source. The rest of `FORMAT.md` is followed by the AI that reads it.
- **Backlinks are searched, not stored.** A page's facts are a tag search; a record's facts are a `source` search; the pages that link a page are a grep of the local copy. Part 3's `links <target>` wraps the three. Nothing holds a fact id but the memory itself, so a replaced fact leaves no stale link.

## Risks / Trade-offs

- [One plugin's column clutters the memory for the others] → Each column has a note, every change is kept with its device, and the cap of 20 columns keeps it small. The person can remove a column.
- [A plugin writes many facts] → The existing per-key limits, 50 facts a call, and each fact's 400-character cap.

- [A pass outlives *Turn off* by up to an hour] → Short pass; the route checks the key each time. Revoking passes on turn-off needs a list per key; not worth it now.
- [Cost after 2026-11-12] → No per-repo charge. Each sync is about 2 to 3 operations; 10,000 a month are free, then $0.15 per 1,000. The 15-minute rule keeps a person near 150 a month. The build checks on staging whether an empty pull or a pass counts as an operation.
- [A sync conflict] → Pages are small and split by subject; part 2 writes one chat's facts and topics at a time and syncs before and after.
- [The account id shows in the remote] → It is in each answer to a signed-in computer only, never in a public file; the site guard still refuses it.

## Migration Plan

Run the setup script for staging, publish, try; then live. No data moves. Rollback: remove the route; webs stay in Artifacts untouched.

# Relay Everything's person spaces

Each person's Relay Everything data lives in their own space: one SQLite-backed Durable Object, opened only for that person's checked sign-in, device key or AI app grant. This page tells how a space is opened, the check that keeps it that way, the shared directory, the space's migrations, the agents' database, sealed recordings and photos, and the ways in that are not a device, such as email. It is part of [the wiki](README.md); the website's [Privacy](../site/src/content/docs/privacy.md) page owns what a person reads about it, and [the plan](../openspec/changes/archive/2026-11-06-relay-person-spaces/design.md) owns why it has this shape.

## How a space is opened

1. The Worker's gate asks [`caller.ts`](../app/worker/apps/relay/caller.ts) who calls: a device key (`Authorization: Bearer rek_…`, looked up by SHA-256 in `relay_keys`), the preview checker (its Client ID's SHA-256 is `RELAY_CHECKER_SHA256`), a session cookie (`__Host-relay_session`), or, on a server that signs in with Access, Access's email. The answer is cached per request, so the route gets the same caller.
2. Only a checked identity becomes a caller, through `vouch` in [`space.ts`](../app/worker/apps/relay/space.ts). A few files may call `vouch`: the caller check, the sign-in, the AI connector's door (`relay-mcp/asker.ts`, for a grant or an API key), the webhooks' queue consumer, and the inbox's lookup ([ways in](#ways-in)).
3. A route calls `spaceOf(env, caller)`. It names the space by the caller's random person id, never by an id from the request, and gives back a `Db` in D1's shape, so each route keeps its own SQL.
4. A device key adds data to its own person's space: `reaches` in `caller.ts` holds it to its routes. A person's routes refuse a key. A `phone` key also reads, to sync its notes: `GET connections` ([`connections.ts`](../app/worker/apps/relay/connections.ts)), the names of its person's AI apps and webhooks with no address, secret or data; `GET notes` ([`note-sync.ts`](../app/worker/apps/relay/note-sync.ts)), the notes changed or deleted since its last sync; and `GET attachment` and `GET audio`, a note's file and a ring note's recording. It changes any note in its space with `PATCH notes`, and deletes one, with its files and recording, with `DELETE notes` ([`delete-note.ts`](../app/worker/apps/relay/delete-note.ts)), which logs one `note.deleted` for the webhooks. It reads no health, place, calendar event, chat or photo, and deletes nothing else. An `api` key reaches only `GET key` here, and an `agent` key, a computer's from `/relay:connect`, only the chat routes and `GET key`; the connector's web API takes both through `apiKeyCaller`, which refuses every other reach ([the connector](stack/relay-ai-connector.md#the-web-api)).
5. A signed-in person writes notes from the page with the phone's routes: `POST`, `PATCH` and `DELETE notes`, and `POST attachments`, through `asDeviceOrPage` in `caller.ts`. A session, or Access's email, writes as the space's own *Web* device, made on the first write like *Email* ([ways in](#ways-in)): `token_client_id` `page:web`, `reaches` `inbox`, no key. So the notes, the phones' sync and the webhooks name *Web*, and `GET notes` gives the page `mine: true` for *Web*'s notes, the only notes it adds files to. A read never makes the device. *Web* has no key, so the list of devices leaves it out and *Turn off* can't reach it. The gate takes a change by session or Access email only with the page's own `Origin`, because a browser sends both cookies from any site. No key gains reach.

The [`Space`](../app/worker/spaces-worker.ts) class lives in its own Worker, `relay-everything-spaces` (`-staging`, `-local`, and `<name>-spaces` on a self-host), bound as `SPACES` by `script_name`, because a Worker that holds a Durable Object class loses its preview links, as with [the live line](stack/live-line.md). Deploy the spaces Worker before the app, so the binding finds its class.

## The one-door rule

Only `space.ts` opens a space, the agents' database or the file store. [`space-access.test.ts`](../app/worker/apps/relay/space-access.test.ts) reads the worker source and fails when another file names `SPACES.`, `WORKBENCHES.`, `idFromName` or `RELAY_BUCKET`, or calls `vouch` outside its allowed files. Don't add an exception: an owner screen or tool that opens another person's space breaks the promise on the privacy page. Route tests show Ana's session, key and AI grant each reach only Ana's rows, with Ben's ids in the request.

## The directory

The shared D1 database keeps only who has an account and how they sign in, in [`20261107120000_relay_people.sql`](../schema/migrations/20261107120000_relay_people.sql): `relay_people` (a random id and the email), `relay_logins` (Apple and Google subjects), `relay_sessions`, `relay_sign_in_codes`, `relay_keys`, and `relay_connect_codes` (the AI connector's single-use codes). [`20261107200000_relay_phone_codes.sql`](../schema/migrations/20261107200000_relay_phone_codes.sql) adds `relay_phone_codes`: a phone's single-use sign-in code, with the SHA-256 of the app's secret, which [`sign-in/phone.ts`](../app/worker/apps/relay/sign-in/phone.ts) trades once for the phone's own key. Each code, session and key is kept only as its SHA-256. [`20261110120000_relay_agent_keys.sql`](../schema/migrations/20261110120000_relay_agent_keys.sql) adds `relay_computer_codes`: a computer's link sign-in, with the SHA-256 of its secret, which [`sign-in/computer.ts`](../app/worker/apps/relay/sign-in/computer.ts) trades once, after the person's *Connect*, for the computer's own key. [`20261108090000_relay_inbox.sql`](../schema/migrations/20261108090000_relay_inbox.sql) adds the inbox's two tables: [ways in](#ways-in). No note, sample, place, chat or recording goes in the directory. The shared tables from before spaces, and the one-time move that copied them into the owner's space, are gone: [`20261107180000_relay_drop_old_tables.sql`](../schema/migrations/20261107180000_relay_drop_old_tables.sql) drops them.

## Space migrations

A space runs [`schema/space-migrations/`](../schema/space-migrations/) in order, in its constructor, and records each step in its `space_migrations` table. A new space table goes in a new numbered file: never edit one a space already ran. [Space migrations](relay-space-migrations.md) tells what each step does and the rules for a step that rebuilds a table.

## The agents' database

Each person also has a second Durable Object, the [`Workbench`](../app/worker/spaces-worker.ts), bound as `WORKBENCHES` by the same `script_name`, named by the person's id. It holds only the tables the agents on the person's computers make: no migration, no `relay_` table, no file key. A Durable Object has one SQLite database, so a separate object is the only way free SQL can't reach the space: a command on `relay_notes` fails as *no such table*. Don't move a Relay Everything table into it, and don't give the space a raw-SQL route instead.

- **The door.** `spaceOf` opens it as `space.workbench`, on first use, for the same checked caller. Deleting the space deletes it first, so *Delete my account* takes both.
- **The routes.** `POST /v1/db` and `GET /v1/db/tables` on the connector's web API, through `computer()` in [`answers.ts`](../app/worker/relay-mcp/answers.ts): only an `agent` key gets in.
- **The limits.** `WORKBENCH_LIMITS` in `spaces-worker.ts`. A step past one throws inside its transaction, so nothing it wrote stays; a SQL error comes back as the answer, never as a crash.
- **Kept apart.** No webhook, export or connector tool reads it, and the server writes no health or location data into it.

A new class needs a new tag in `migrations` of [`wrangler.spaces.jsonc`](../app/wrangler.spaces.jsonc) and the self-host's `spaces.template.jsonc`, and a binding in each Worker that binds `SPACES`; [`bindings.test.mjs`](../app/self-host/bindings.test.mjs) checks both bindings. The website owns what a person reads: [Your agents' database](../site/src/content/docs/api/agents-database.md).

## Ways in

A way in that is not a device, such as email, hands each message to one inbox, [`inbox/receive.ts`](../app/worker/apps/relay/inbox/receive.ts). The inbox makes one note from the way in's own device in the space (*Email*, `reaches` `inbox`, `token_client_id` `inbox:email`), seals its files as a phone's are, and stores a repeat once by the message's id. A later way in, such as text messages, adds a channel and calls the same inbox. The website owns what a person reads: [Email notes](../site/src/content/docs/app/email.md).

1. **Find the person before a space opens.** [`inbox/links.ts`](../app/worker/apps/relay/inbox/links.ts) looks up `relay_inbox_links` by an HMAC-SHA-256 of the address, under the server's secret `RELAY_INBOX_HMAC_KEY`, then calls `vouch("inbox", …)`. The HMAC keys the lookup; the row's `shown` column holds the address's local part in plain text, so the card can show it. The mail domain is public, so a copy of the directory gives each person's address, and with it a way to add notes. *New address* is the remedy for a leak: it deletes the old row, so mail to the old one finds no one.
2. **Check the sender of `notes@`.** [`inbox/email.ts`](../app/worker/apps/relay/inbox/email.ts) takes `notes@` mail only by its one `From` and the topmost `Authentication-Results` (or ARC) header from `mx.cloudflare.net`: DMARC passed, or aligned SPF and DKIM. Mail that fails is dropped with no answer; the server never sends mail.
3. **Keep mail for an email with no account.** [`inbox/held.ts`](../app/worker/apps/relay/inbox/held.ts) seals it with AES-256-GCM under a key made by HKDF from the server's key and the sender's email, which the server does not keep: the row in `relay_inbox_held` holds the sealed body, its files go under `held/<sender HMAC>/` in the bucket. Each email keeps at most 100 messages and 50 MB. Each email-code, Apple or Google sign-in claims any still waiting for the person's email, after the answer, in order of sending; a lookup by the sender HMAC comes first, so a sign-in with nothing waiting costs one query. A claim that stops partway, such as at `waitUntil`'s time limit, finishes at a later sign-in, and the note's `clientId` stores each message once.
4. **Sweep it.** The shared server's Cron Trigger deletes kept mail older than 30 days each day; `POST inbox/sweep` runs it by hand on staging. A self-host has no cron, so each new kept mail runs the sweep too.

Email Routing sends a mail domain's mail to the server Worker's `email()` handler, in [`relay-only.ts`](../app/worker/relay-only.ts). The live server's domain is the website's zone itself, `relayeverything.com`, so the addresses are `notes@` and `notes-<code>@relayeverything.com`; staging's is the subdomain `in-staging.`. Each is set as `RELAY_INBOX_MAIL_DOMAIN` in [`wrangler.relay.jsonc`](../app/wrangler.relay.jsonc), and the server refuses mail to any other domain. A server with no domain or no key refuses all mail. Add or remove a subdomain in the dashboard, under the zone's *Email Routing* → *Settings* → *Subdomains*, which also adds or removes its MX and SPF records. The repository's token gets an Authentication error on the Email Routing settings endpoint, and those DNS records are read-only. With the person's yes, a [one-off 15-minute token](stack/cloudflare-credentials.md#the-widen-is-pre-authorized) for the zone with *Zone Settings Write*, *DNS Write* and *Email Routing Rules Write* can do it: `DELETE zones/<zone>/email/routing/dns` with `{"name": "<subdomain>"}` removes one. The token can still add rules through `email/routing/rules`. A rule matches one address only, and a zone has one catch-all: live's catch-all sends each apex address with no rule of its own to `relay-everything-server`, and staging gets one literal rule for each test address, such as `notes@in-staging.`, to `relay-everything-server-staging`. A literal rule wins over the catch-all, so `matt@` and `privacy@` keep their own rules and never reach the server; leave them as they are.

## Recordings, note files and photos

A recording's file store key is `people/<person id>/<note id>`, a note file's is `people/<person id>/attachments/<file id>`, and a photo's is `people/<person id>/photos/<photo id>`. Each is sealed with AES-256-GCM: a fresh 12-byte IV per object, the space's own 256-bit file key from `space_keys`, and the store key as associated data, so a copy under another name fails to open. `audio.ts`, [`attachments.ts`](../app/worker/apps/relay/attachments.ts) and the connector's `read_photo` open a file only through the caller's space. A phone key opens a note's file and a ring note's recording, to sync them; it can only add a photo, with `POST photos`.

`POST photos/delete` deletes every photo file and row in the space, and keeps the recordings and note files. Only the person's page session can call it, not a key. Deleting the space deletes the file key, and account deletion also deletes every object under the prefix.

## Webhooks

The send log, `relay_outbox`, and `relay_webhooks` live in each space. A webhook takes notes always, and `health`, `locations`, `calendar` and `photos` only when its owner ticks them; a changed or removed event goes out again as `calendar.events`, with its `status`. Each stored file goes as its own `note.file`, after its note, under the Notes kind: [`send.ts`](../app/worker/apps/relay/webhooks/send.ts) writes its base64 into one byte array, not a string, so a 25 MB file stays inside a Worker's memory. Each photo goes alone as `photo.created`, built the same way. A `413` answer to a `note.file` or a `photo.created` skips that file and names it in the card's last answer; every other failure retries. A queue message carries the webhook and its person, and the consumer opens that person's space. Each space with a webhook sets an alarm every 15 minutes, which wakes any webhook left behind and drops tries older than 30 days. No job walks over all spaces, and a space with no webhook costs nothing.

Each kind of data a webhook takes comes from one list, checked by a test: [add a kind of data](relay-webhook-changes.md).

To check webhooks on staging, use a public `https` receiver, because the server refuses a private address. Run the website's example receiver, `site/public/webhooks/receiver.mjs`, behind a quick tunnel (`cloudflared tunnel --url http://127.0.0.1:<port>`), with one receiver for each webhook, because each webhook has its own secret. A failed answer is tried again after 30 seconds, then 2 minutes: `DELAYS` in [`webhooks/send.ts`](../app/worker/apps/relay/webhooks/send.ts) holds the waits. When no inbox gets the email code, add a test person and a session to the staging database (`npx wrangler d1 execute DB --remote --env staging -c wrangler.relay.jsonc`), send the session as the `__Host-relay_session` cookie, and delete the person with `POST account-delete` after.

The phone can also send format v1 itself, straight to one webhook, with no space: [`mobile/lib/data/webhook.dart`](../mobile/lib/data/webhook.dart). Its fixtures in `mobile/test/fixtures/webhook/` keep it and [`format.ts`](../app/worker/apps/relay/webhooks/format.ts) the same.

## The Workers and their order

Three Workers serve Relay Everything, and each deploy goes in this order, because Cloudflare refuses a binding to a Worker that does not exist:

1. The spaces Worker, [`app/wrangler.spaces.jsonc`](../app/wrangler.spaces.jsonc): the `Space` and `Workbench` classes, with no web address. Wrangler bundles it alone, with no Vite, so it loads no route code (`api/contract.ts`) and no `import.meta.glob`: Cloudflare refuses a Worker that fails at its start. Put a list that a route and a webhook both need in `apps/relay/store.ts`, not in the route. [`spaces-worker.test.ts`](../app/worker/spaces-worker.test.ts) fails, and names the chain of files, when the spaces Worker loads such code.
2. The AI connector, [`app/wrangler.relay-mcp.jsonc`](../app/wrangler.relay-mcp.jsonc), which binds `SPACES`.
3. The shared server, [`app/wrangler.relay.jsonc`](../app/wrangler.relay.jsonc), and the company app, [`app/wrangler.jsonc`](../app/wrangler.jsonc), which both bind `SPACES` and the connector.

A publish deploys the live spaces Worker, the connector and the company app ([`scripts/cf-deploy.sh`](../scripts/cf-deploy.sh)), but not the shared server or any staging Worker. So after each publish, run [`scripts/publish-relay-server.mjs`](../scripts/publish-relay-server.mjs). It exports the published commit to a new folder, runs `npm ci` in its `app/`, and deploys in this order: the staging knowledge web's start, the staging spaces Worker, the staging connector, the staging shared server, then the live start and the live shared server ([the knowledge web](stack/relay-knowledge-web.md#the-knowledge-web)). Before each deploy it checks the Worker name, so a build that missed its environment never lands on live. It stops at the first failure, so a staging failure leaves live as it was.

| When | Run |
|---|---|
| After each publish | `node scripts/publish-relay-server.mjs` |
| To try a branch on staging only | `node scripts/publish-relay-server.mjs --ref HEAD --staging-only` |
| To build with no deploy | `node scripts/publish-relay-server.mjs --ref HEAD --dry-run` |

It prints one line: `result=deployed ref=<commit> workers=<each Worker>`, `result=dry-run ...`, or `result=failed step=<step>`. It applies no D1 migrations: each branch's preview applied them to the staging database before the merge. To go back, run it again with `--ref <earlier commit>`, or `npx wrangler rollback` for one Worker.

A preview deploys only the company app, so deploy a branch's spaces Worker from `app/` by hand: `npx wrangler deploy -c wrangler.spaces.jsonc --env staging`. Every branch, and each publish, deploys to the same staging spaces Worker, so a deploy from one drops another branch's space steps: a staging check that fails on a missing table or a CHECK rule may only need your branch deployed again. Spaces track each step by name, so two branches' `0003_` files both run. Each chat's checks also share staging's people: another chat can delete your test account or deploy over your check. So before a staging check, ask the chats that publish (`ListAgents`) to hold, and deploy your branch just before the check.

The shared server shares the company app's database, bucket and queue. On production the company app keeps the queue's one consumer. Staging is different: previews reach no other Worker's objects ([the live line](stack/live-line.md)), so the company app's staging Worker has no `SPACES`, its relay routes answer 503, and the staging shared server has its own queue, `relay-everything-server-webhooks-staging`. The staging spaces Worker sends its 15-minute catch-up to that queue too; [`queue-pairing.test.ts`](../app/worker/queue-pairing.test.ts) fails when an environment's catch-up goes to a queue that no Worker with `SPACES` reads. So check a person's data on `app-staging.relayeverything.com`. It runs the last published commit only when someone ran the command above, so first compare `npx wrangler deployments list --name relay-everything-server-staging` with the newest merge. Then sign in with an email code, make a key with *Add a device*, send with it, then turn the key off. To see a branch's own Relay Everything page, such as the webhook form, run it on this computer: from `app/`, run `npx wrangler d1 migrations apply DB --local --env local`, add the local sign-in with `npx wrangler d1 execute DB --local --env local --command "INSERT INTO relay_people (id, email, created_at) VALUES ('local-dev', 'dev@example.com', 0)"`, build the page with `node ../scripts/build-relay-web.mjs`, because the company app's build makes none, then `npm run dev` and open `/apps/relay/`. That server runs the last published commit, or a branch's `--staging-only` run, not the branch, but it shares the branch's staging database. The shared server answers at `app.relayeverything.com`, and the company app at `admin.relayeverything.com`. The shared server, and a self-hosted one, open the page at the top address, `/`; the page's files, API and sign-in stay under `/apps/relay/`, which opens the page too. The company app serves no copy of the page: its *Relay Everything* card links to `https://app.relayeverything.com/`. A Worker's custom domain has one Worker: to move an address, take it off the old Worker first, then deploy the new one, which claims it.

The page is the Flutter app drawn on one canvas, so a headless browser such as [`agent-browser`](../.agents/skills/agent-browser/SKILL.md) can't click its text. Sign in with the staging session cookie (`cookies set __Host-relay_session … --url https://app-staging.relayeverything.com/ --secure --httpOnly`), click at a point with `mouse move`, `mouse down` and `mouse up`, and type with `keyboard type`. The paperclip's file chooser opens only for a person: check a file with a `drop` event that carries a `DataTransfer`, which takes the same upload path. An `open` that changes only the `#` does not reload the page: open `about:blank` first. The assistant's own browser (`browse.mjs`) shows the page blank, live or on staging; use a Chromium, such as Playwright's headless one started with `--use-angle=swiftshader`.

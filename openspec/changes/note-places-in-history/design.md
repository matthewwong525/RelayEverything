# Design

## Context

- **Phone.** `keepNote` and `keepRecording` in `mobile/lib/controller.dart` take `pin`, and with `_settings.pinNotes` keep the note with `waitForPin` (`notes.pinning = 1` in `lib/data/store.dart`), then `_pinThenSync` takes a fix through `places.here(name: sending)` and `store.settlePin` writes it into the note's body as `LocalNote.pin` and queues its upload. `Settings.pinNotes` defaults on for the first version's settings. `_entryOfLocal` shows `pin.place ?? 'Pinned'`; `timeline.dart`, `days.dart` (search) and `note_editor.dart` read `Entry.place`; `web/web_relay.dart` fills it from `GET notes`; `shortcuts/bridge.dart` and `ios/Runner/RelayIntents.swift` give `place` back to Shortcuts. Location points go through `store.addPoint(pin, send: locationSend)` into `points` (raw, queued by `queuePoints`) and `track` (stays and trips), and flush to `Settings.privatePlace`.
- **Server.** `relay_notes` holds `lat`, `lon`, `accuracy`, `place`, `place_from`, with a table CHECK that `lat`, `lon` and `place_from` are null together (`0001_relay.sql`). `relay_attachments.note_id` and `relay_note_changes.note_id` reference it `ON DELETE CASCADE`. `relay_note_changes_changed` fires `AFTER UPDATE OF text, lat, place, edited_at, audio_key`. The ring's `note.updated` trigger for places from history was dropped in `0005_no_pebble.sql`. `add-note.ts` stores a typed note's place; `notes.ts` (POST notes) and `relay-mcp/inputs.ts` (`add_note`) take `lat`, `lon`, `accuracy`, `place`. `queries.ts` `shaped` gives `place`, read by `timeline.ts`, `note-sync.ts`, the connector (`openapi.ts` note shape) and `webhooks/format.ts` `noteOf`. The connector's `fetch` already adds `placesNearby` from `visits` around the note's time.
- `relay_locations` has `UNIQUE (device_id, at)`, `accuracy REAL NOT NULL`, and `relay_outbox_location` logs each insert for webhooks.

## Goals / Non-Goals

**Goals:** one home for where the person was; a point per note while location history is on, with no setting; no note answer or message holds a place; old places kept as points, once.

**Non-Goals:** a place shown by time under a note; a new read; a change to stays and trips, to phone-key reach, or to `Sender` and the outbox routing.

## Decisions

- **The phone's point.** `keepNote` and `keepRecording` lose `pin`'s place meaning: the parameter becomes `point` (`false` for a note made earlier than now, as today). With `_settings.history` on and `point` true, the note is kept and queued at once, never waiting, and a tracked job (`_pointThenSync`, kept in the set `settled()` waits on, so Shortcuts still lets the round finish) runs `places.here(name: _settings.sending)`, then `store.addPoint(Pin(at: note.createdAt, lat, lon, accuracy, place), send: _settings.locationSend)`, then `sync()`. History off: no `here()` call. A failed fix keeps nothing. The point's `at` is the note's time, so it matches by time exactly; `UNIQUE (device_id, at)` and the phone's `INSERT OR IGNORE` keep one per time. Alternative: the fix's own time, rejected because a by-time lookup then misses by a few seconds and a note can share none. An in-app voice note (`_keepVoice`) takes its fix as the recording starts, because `createdAt` is the start and a recording can last 5 minutes; it becomes the point only when the note is kept, so a cancelled, too-short or unsaved recording adds none.
- **Phone storage.** `LocalNote.pin`, `pinning`, `waitForPin`, `settlePin`, `settleOpenPins`, `Settings.pinNotes`, `setPinNotes` (both `Relay` implementations) and the Settings row go. A store version step, in one transaction: for each note body with a `pin` whose note is not yet sent and while `history` is on, `addPoint` at the note's `createdAt`; then rewrite every body without `lat`, `lon`, `accuracy`, `place`; then set `pinning = 0` and queue those notes when sending is on. The `pinning` column stays, unused, as SQLite columns do. `Pin` keeps its name, as it is the point type.
- **Readers in the app.** `Entry.place` goes; the note row's meta, the note editor's line and search drop it. `web_relay.dart` stops reading `place`. Shortcuts' note entity loses `place` in `bridge.dart` and `RelayIntents.swift`.
- **The server keeps the place columns, empty.** Rebuilding `relay_notes` to drop them means `DROP TABLE relay_notes`, whose implicit delete runs the `ON DELETE CASCADE` on files and note changes even with the foreign-key check deferred; D1 can't turn foreign keys off. `ALTER TABLE … DROP COLUMN` refuses columns named in the table CHECK. So `0017_note_places.sql` empties them; no code reads or writes them after it. A comment in the migration and in `connections/your-database.md` says so.
- **`0017_note_places.sql`.** (1) Drop `relay_outbox_location`. (2) `INSERT INTO relay_locations (device_id, at, lat, lon, accuracy, place, created_at) SELECT device_id, recorded_at, lat, lon, COALESCE(accuracy, 0), place, <now ms> FROM relay_notes WHERE lat IS NOT NULL ON CONFLICT (device_id, at) DO NOTHING`. (3) Make `relay_outbox_location` again as `0014_nights.sql` has it, so the moved points send no webhook message. (4) Make `relay_note_changes_changed` again as `AFTER UPDATE OF text, edited_at, audio_key`. (5) `UPDATE relay_notes SET lat = NULL, lon = NULL, accuracy = NULL, place = NULL, place_from = NULL WHERE lat IS NOT NULL OR accuracy IS NOT NULL OR place IS NOT NULL` — after (4), so it makes no note change and no phone pulls every note again. A phone's stored copy keeps its old `place` key until the body rewrite in its own store step drops it.
- **A place on a new note.** `addNote` (`add-note.ts`) keeps taking `lat`, `lon`, `accuracy`, `place` from POST notes and `add_note`, and in the same batch inserts the note with no place and one `relay_locations` row of the same device at `createdAt` (`ON CONFLICT DO NOTHING`), only when the note itself was new. Its `relay_outbox_location` row sends the point to webhooks ticked for location. The field descriptions in `notes.ts` and `inputs.ts` say the place becomes a location point. Alternative: refuse or drop the fields, rejected because an older phone's notes would then fail or lose their place.
- **Answers and messages.** `shaped` in `queries.ts` drops `place`, and `Row` and `COLUMNS` their place columns; the `place` schema in `timeline.ts`, `note-sync.ts` and `relay-mcp/openapi.ts` goes from the note shape. `noteOf` in `webhooks/format.ts` drops `place`, the `NoteRow` place fields go, and the published schema and `site/public/webhooks/receiver.mjs` follow (the receiver keeps its columns, written null, so an existing database still opens). `kinds.ts` says notes come *with their words and recording*. `npm run relay:api-doc` writes the API reference.

## Risks / Trade-offs

- **A webhook receiver that reads `note.place` gets nothing.** Version 1 may change before the public release, and the website's format page says so; the place still reaches location webhooks as a point.
- **An old day may show one more place.** A moved point outside every stay and trip shows in that day's places, as any loose point does. That is the place the note was written.
- **Offline pins go.** A note kept signed out with *Pin notes* on loses its place, since no location history exists to hold it. The plan says it can't be undone.
- **Build order.** The `relay-settings` delta modifies a requirement that `settings-same-everywhere` adds; archive refuses it until that change ships. The first task checks it has.
